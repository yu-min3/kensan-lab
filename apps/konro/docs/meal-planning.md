# 買い物・作り置き・調理の接続

保存済みレシピから献立と買い物リストを作り、同じ版・分量で調理を始める。
AI提案は既存agent-runtimeの汎用`text` profileを使用する。モデル認証・購読管理はruntime側に置く。

## 日常の操作

1. 一覧で料理を選び「買い物」へ進む。人数未登録なら元の分量に対する倍率を指定する。
2. 原文と集約量を確認し、手持ち・購入状態を保存する。数量変更はプレビューしてから反映する。
3. 「この分量で調理」で献立作成時のレシピ版を使う。材料だけを換算し、手順内の数値は原文を保持する。
4. 「作り置き」ではイメージ・品数・各料理の人数を指定する。必須条件は詳細欄で指定し、固定・1品交換・採用ができる。
5. 調理終了時の実績記録は任意。提案採用と実際の調理は別に保存し、履歴を取消・復元できる。

タグは分類内OR・分類間AND。未知タグはその他へ残す。画像・タイトルは検索元ページ、色付きの「取り込む」は独立した操作。
調理session・通知済み状態・料理別の位置は画面から独立して保持する。

## データの契約

`KONRO_DATA_DIR`内でレシピMarkdownとは分けてatomic保存する。単一serverで運用する。

| パス | 内容 |
|---|---|
| `tag-taxonomy.json` | 版付き分類辞書 |
| `meal-plans/` | 献立、レシピの固定版、倍率、材料補正、買い物状態、操作receipt |
| `menu-proposals/` | 条件・候補・好み・方式の固定版、runtime job、採用receipt |
| `feedback/` / `cook-history/` | 固定・交換・採用と実調理の別記録 |
| `.settings/meal-preferences.json` | 明示的な好みと確認待ち候補 |
| `planning-policies/` / `planning-evaluations/` / `planning-policy.json` | 改善候補・同一ケースの比較・現行方式 |

更新はrevision/operation IDで競合と再送を扱う。買い物の元材料量が変わると購入済み・手持ちを再確認する。
材料は有理数で計算し原表記・出典を保持する。異単位や不明量は無理に加算しない。
除外材料は原文と解析済み材料名を照合し、材料計算と同じ別名正規化を使う。

## AIと自己改善の境界

人数が明確で材料・手順のあるレシピだけを候補にする。ID・品数・主副菜・固定品・除外条件をアプリで検証する。
無効出力の修正再試行は1回まで。旧候補版・好み版・方式版が変わった案は新規採用できない。
新規受付前に以前のjobを再照合し、進行中なら`GET /api/v1/menu-proposals/active`から画面へ復帰できる。
AI未接続でも「条件だけで簡易提案」を明示的に使える。簡易提案は自由文を解釈しない。

方式候補は`POST /api/v1/planning-policies`で保存し、`/compare`で同一条件・候補による比較記録を作る。
`/activate`には候補version・comparisonId・現行versionのexpectedを渡す。以前の方式も比較して戻せる。
このAPIは改善効果を証明しない。自動学習・自動昇格・履歴からの推定生成は将来の拡張で、現段階では実施しない。

## 制限と復旧

- 買い物の未送信操作は端末ごとに1件保持し、再送か明示取消まで次の変更を止める。
- 調理sessionと買い物キャッシュはlocalStorageに保存する。通信失敗時は消去せず画面から再送する。
- AI提案品質とバックグラウンド通知は実際の料理・端末で継続確認する。
- リリース前にvolumeをsnapshot/backupし、アプリを戻すときは旧image tagへGitOpsで戻す。追加JSONは消さず保持する。

検証は`make test`と`e2e/{cooking,improvements,shopping,proposals,library,photo}.mjs`。
ブラウザ試験では独立してbuildした`KONRO_TEST_BINARY`と必要なら`CHROME_BINARY`を指定する。
