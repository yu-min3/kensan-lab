omarkey VM と自動開発基盤の併用判断

2026-09-29 · 原本 apps/sense-dev/docs/host-coexistence-decision.md

▲ Yu の判断待ち

止まっているのは sense への初回配置。 omarkey の sense-llm と sense-desktop は自動開発チームではない。コードと独立レビューは手元で進んでいるが、controller は sense に未導入、実モデルの自動運転も未開始。

推奨: VM 2台を維持したまま、mock-only の host service 併用を条件付きで許可。
直前 baseline と独立した host_install=allow が成立するまで転送・起動しない。予想外の競合や資源不足なら中止する。

なぜ止めたか

9/27 に k3s が停止され、libvirt VM 2台が稼働し始めた時点では用途と所有者が不明だったため、固定ポリシーの「並行作業との調整」を満たせなかった。今回、omarkey 用と判明した。残る判断は VM を動かしたまま host service を併用してよいか。確認の切り方が曖昧だったのは僕の側の問題。

選択肢

選択肢判定判断理由・残る証拠
A. VM を維持して host に mock-only 配置採用推奨goal の host systemd 方針を保つ。専用 user/dir/unit のみ新設し、直前調査と独立 Gate で止められる
B. omarkey 作業後まで延期採用可VM への影響を避けられるが、private-ready の実機検証は進まない
C. VM を停止して容量を作る却下omarkey の別目的を損なう。今回の許可範囲外
D. VM 内や cluster Pod に controller を配置却下host systemd と障害分離の契約を変更する

A を選ぶ場合の実行境界

  1. VM/k3s/資源、専用 user/group/path/unit/port、復旧経路を直前に read-only 確認。変化・競合・資源逼迫なら止める。
  2. 固定 source/artifact/policy/期限と直前 baseline を、別 reviewer が host_install として判定。allow 以外では転送もしない。
  3. allow 後、固定 hash の script を root 管理下で照合し、127.0.0.1:8787 -mock-worker の service のみ導入。VM・k3s・Cloudflare は操作しない。
  4. 継続 event、停止・復元、別ホストから IPv4/IPv6 直結拒否と既存公開経路を実測。未確認なら private-ready としない。
● 今回の承認に含めない

host reboot、VM 停止・設定変更、k3s 再起動、実モデル運転、日報送信、GitHub 操作、Cloudflare・外部公開。最初の配置は模擬運転であり、Fable→Astra→Sol→Opus の常駐チーム開始ではない。

Yu に決めてほしいこと

「VM を止めずに、条件付き host 併用で進めてよい」か、「omarkey 作業後まで延期」か。前者でも直前調査と独立 Gate が不合格なら導入しない。
