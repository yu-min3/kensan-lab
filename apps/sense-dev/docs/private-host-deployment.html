導入境界

✓ 専用範囲 kensan-dev-controller.service、/opt/kensan-dev、/var/lib/kensan-dev、専用 OS user のみ。

✓ 現行候補 独立 Astra reviewer が source ee431b9 の clean archive から再buildし、候補 binary の SHA-256 6cbbc12f…f3c0b2 と一致。固定 manifest は private-bootstrap-candidate-ee431b9.json、判定は private-bootstrap-review-ee431b9.json。rollback の隔離 fixture 10件も合格。code_candidate=allow だが host_install=needs_human、execution_authorized=false。

▲ 事前検査 既存 user・dir・unit/drop-in・systemdロード状態を拒否。port調査の失敗と並行 install も拒否。3入力を root 専用 staging にコピーして hash 検証し、その複製だけを配置。daemon-reload 後、実効 unit を enable 前に照合。script 自身も固定 hash で root 管理の実行経路へ。

▲ 停止・復旧 rollback <unit-sha256> <binary-sha256> は固定 hash と実効 unit が一致する場合だけ当該 service を停止・無効化。不一致なら停止せず調査。台帳・token・binary・unit は保持する。

再開の順序

  1. 別作業の所有者・host 利用範囲と現 k3s/libvirt/VM・available memory を確認する。
  2. 固定候補の source SHA、policy、期限、binary・tokens・unit・script hash、rollback と直前 baseline を独立 reviewer が実機操作として別判定する。
  3. allow 後に初回 service を導入。read-only smoke で実効 unit・MainPID・socket 所有 PID・稼働 binary hash を結び、loopback 待受を確認する。
  4. 別ホストの private-route-probe で LAN IPv4/global IPv6:8787 を検査し、direct_refused のみ成功、timeout/経路なしは未知と記録する。既存 tunnel/proxy/Ingress/CI と router/firewall は別途照合。直結拒否と smoke だけでは非公開を証明しない。
  5. 停止・復元を検証し、未確認なら private-ready としない。
